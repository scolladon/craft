# Plan — planner RED-label audit

> Source: design doc `docs/contributing/design/planner-red-label-audit.md` · ADRs 407, 408, 409, 410, 411, 412
> The plan is the implementation script AND the knowledge handoff. Part agents start
> with zero context: whatever a part block omits is paid later as agent rediscovery.
> `plan-lint.sh` enforces the schema below — the plan phase cannot close without it.

## Sizing rules

- Every part costs a full agent lifecycle (spin-up, zero-context rebuild, gate) — it
  must earn it. No standalone test-only parts for FEATURE code: coverage/interop/property
  tests fold into the implementation part whose code they exercise. EXCEPTION:
  test-infra-only and docs-only parts (tooling config, test helpers, fixtures,
  harness/ADV/property suites, docs/prose) with no `src/` delta ARE standalone — they
  have no implementation part to fold into.
- A part that would be a pure test pass over already-landed code merges into its
  neighbour.
- A part should land in ~100 tool calls. More than ~5 RED→GREEN cycles, or more than 6
  files in its `### Context` block, is two parts. What counts is a backticked path:
  backtick the files the part CREATES or EDITS, and write read-only reference paths in
  plain text.

**How this plan applies them.** Two parts, as the design's "Delivery shape" fixes. Part 1: a
prose edit to `agents/planner.md`, a two-line comment in `templates/plan.md`, and the six
adapter mirrors regenerated by script. Part 2: one line of `contracts/construction.md`, one
line of `agents/part-implementer.md`, and that role's six mirrors. No `engine/src/` delta,
three edit cycles per part. Splitting either part would pay two agent lifecycles for text
edits whose bytes the design already fixes, and the mirrors cannot land apart from their agent
edit (CI's drift check would be red in between). Part 2 follows Part 1 because the contract
names a plan `GUARD` entry, which Part 1 introduces; it stays separate because it changes a
different role's contract and reverts on its own.

- **No unit-test RED, stated honestly.** No test reads planner prose, the template's TDD
  comment or the implementer's handback line, and the one test that reads the construction
  contract pins only markers the edit keeps. The design's Test strategy rules out adding one:
  a string-equality test would only repeat the file. The REDs below are the mirror drift check
  (a real CI failure between the agent edit and the sync) and greps that prove the new text is
  absent before its edit. Checks that already pass before any edit are labelled `GUARD`, never RED.
- **Paid evals are not a part.** The before and after `planning-plan-lints` runs per agent
  tier (design § Test strategy, ADRs 410 and 411) are maintainer-run evidence outside this
  plan. The before runs go on `main`, which this branch does not touch until merge. No part
  runs `claude plugin eval` or any judge replay.
- **R4 is not a part.** Closing the BACKLOG entry "The planner labels an already-passing test
  as RED" with the before/after hand counts belongs to the documentation phase, after the
  maintainer's runs. No part touches `BACKLOG.md`.
- **README corpus count.** The plan commit already bumps README.md l. 180 from
  "[33 parted plans]" to "[34 parted plans]". Neither part adds a design doc, plan or ADR, so
  neither touches README.md.

**Public surface.** The plan introduces no exported code symbol. The non-code surfaces it
edits and their downstream gates, each pre-paid in the part that edits it:

| Surface | Downstream gates |
|---|---|
| `agents/planner.md` body (shared agent prompt) | six adapter mirrors via `scripts/sync-adapter-agents.sh --write`, checked by `--check` inside `scripts/ci.sh`; touched-`.md` prose lint |
| `templates/plan.md` `### TDD steps` comment | `test/plan-doc-fences.test.js` (fence balance over every plan and the template; the comment adds no fence); plan-lint does not read comment text; touched-`.md` prose lint |
| `contracts/construction.md` line 1 (construction bundle, concatenated into every implementation spawn by `engine/bin/contract-assemble.js`) — Part 2 | `engine/test/contract-equivalence.test.js` `PHASE_EXPECTATIONS.construction` markers (`RED→GREEN→REFACTOR`, `atomic commit`, `sut`: all kept); `contracts-lint` (bundle non-empty, no "retrieval"); touched-`.md` prose lint |
| `agents/part-implementer.md` body (shared agent prompt) — Part 2 | six adapter mirrors via `scripts/sync-adapter-agents.sh --write`, checked by `--check` inside `scripts/ci.sh`; touched-`.md` prose lint |

**Binding for each part.**

- No provenance references (ADR numbers, design ids, phase or backlog ids) in
  `agents/planner.md`, `templates/plan.md`, `contracts/construction.md` or
  `agents/part-implementer.md`. The design's verbatim text cites none.
- No suppression directives. Never hand-edit a mirror under `adapters/`.
- Commit only the eight files the part names (`git add <path>…` + `git commit`); never touch the
  branch, the stash, or other files.
- Any command whose output may exceed ~100 lines writes to a scratch file; read back with
  `tail`/`grep`.
- Avoid the prose-lint ban list (`engine/src/prose-lint-main.js` `BAN_LIST`: delve, leverage,
  seamless, robust, "it's important to note", "in conclusion"). The design's text avoids it.

## Decision candidates

None open. ADRs 407–412 adopt every design recommendation (D-a (b): agent plus template;
D-b (b): label plus ordering; D-c (a): fixed token `GUARD`; D-d (a) and D-e (a): baseline and
hand count, both outside the plan; ADR-412 option 1: the implementer contract and handback
line change here), and the design fixes the replacement bytes for all four edited files. No
plan-level choice is left: the part order is the design's, and inside each part the
agent-then-sync order is forced by the drift check, not chosen.
